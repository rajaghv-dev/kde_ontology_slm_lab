# 06 — Dataset generation strategy

The dataset is where your design choices become the model's behaviour. A KDE-specialised SLM is only as good as the JSONL records you train on. This chapter walks the six template families in [../src/dataset/qa_generator.py](../src/dataset/qa_generator.py), the canonical record schema, the quality rules we enforce (evidence on every architecture/debugging answer, "I don't know" examples, ambiguity examples, stale-code examples), and the discipline that keeps hallucinated facts out of training.

## Why generate from the graph

You could write KDE Q&A by hand. People do. It does not scale, and it bakes in the writer's particular blind spots. The lab takes the opposite route: every dataset example is generated by walking the ontology graph, and every example carries an `evidence` list pointing back at the graph nodes that justify it.

That has two consequences:

1. **Truth is locally checkable.** If a record says *"KFileSearcher emits resultsReady"*, the evidence list names the file, the line, and the symbol. The grader can verify the claim and the dataset filter can reject any record whose evidence does not back it up.
2. **The graph is the bottleneck.** If the ontology is missing a relation, the dataset cannot teach it. That keeps the model honest about what it knows and what it does not.

## The six template families

The templates live at the bottom of [../src/dataset/qa_generator.py](../src/dataset/qa_generator.py) in the `TEMPLATES` tuple:

| Template                       | `task_type`        | Question shape                                                | Mini-repo output                              |
|--------------------------------|--------------------|----------------------------------------------------------------|------------------------------------------------|
| `template_signal_emission`     | `architecture_qa`  | *Which signals does {Class} emit?*                            | KFileSearcher emits resultsReady, ...          |
| `template_config_keys`         | `code_navigation`  | *Which KConfig keys does {Class} read at runtime?*            | KFileSearcher reads MaxResults.                |
| `template_qml_backend`         | `code_navigation`  | *Which C++ class is the QML component {Q} backed by?*         | ApplicationWindow is backed by KFileSearcher.  |
| `template_log_to_component`    | `debugging`        | *When debugging {Class}, which log category to enable?*       | Enable minisearch.backend.                     |
| `template_dbus_methods`        | `tool_use`         | *Which D-Bus methods does {Interface} expose?*                | org.kde.minisearch exposes searchPath, ...     |
| `template_refusal`             | `architecture_qa`  | *What signal does the imaginary KFooBarMaker emit?*           | "I do not see a class named KFooBarMaker."     |

Six templates produce five task types. That is intentional. The task type is what the adapter router in chapter [07_training_recipes.md](07_training_recipes.md) keys off of; multiple templates feeding the same task type gives the model varied surface form for the same underlying skill.

Each template walks the graph with the named queries from [../src/graph/queries.py](../src/graph/queries.py). For example, `template_signal_emission`:

```python
for cls in nodes_of_type(g, "CppClass"):
    sigs = signals_emitted_by(g, cls)
    if not sigs:
        continue
    ...
```

If a class has no signals, no record is produced. The pipeline never invents a signal to fill a quota.

## The JSONL schema

Each record is one JSON object per line. The shape:

```json
{
  "id": "kde:DatasetExample:<hash>",
  "task_type": "architecture_qa",
  "instruction": "Which signals does the KFileSearcher class emit?",
  "input": "",
  "output": "KFileSearcher emits the following signals: resultsReady, searchFailed, currentPathChanged, maxResultsChanged.",
  "evidence": [
    {"file": "...kfilesearcher.h", "line_start": 12, "line_end": 12,
     "symbol": "KFileSearcher", "relation": "DEFINES", "confidence": 0.9},
    {"file": "...kfilesearcher.h", "line_start": 32, "line_end": 32,
     "symbol": "resultsReady", "relation": "EMITS", "confidence": 0.9}
  ],
  "negative_examples": [],
  "metadata": {
    "generated_by": "rule",
    "difficulty": "easy",
    "license": "synthetic",
    "split": "train",
    "component": "KFileSearcher",
    "repo": "mini_kde_repo"
  }
}
```

Key fields:

- **`id`**. Deterministic via `make_id("DatasetExample", f"{task_type}::{instruction[:60]}")`. Re-running the pipeline produces the same ids, which lets the dataset writer be idempotent.
- **`instruction`** + **`input`**. The instruction is the question. The `input` is reserved for retrieval-augmented variants where you pass evidence text alongside the question; v0 leaves it empty.
- **`output`**. The reference answer. The grader compares against `must_mention` and `must_not_mention` from the eval suite.
- **`evidence`**. The proof. Every architecture and debugging answer in the dataset must carry at least one evidence entry whose `file` and `symbol` are non-empty.
- **`negative_examples`**. Hard-negatives for the same instruction. v0 leaves this empty; v0.1 will populate it for the preference-tuning stage.
- **`metadata`**. Bookkeeping. `split` ("train" / "eval"), `component` (used for split rules and adapter routing), `difficulty`, `license`.

The schema test lives at [../tests/test_dataset_jsonl_schema.py](../tests/test_dataset_jsonl_schema.py); it is the integration test that fails loudest when someone breaks the schema.

## The seven quality rules

Rules we enforce, in roughly the order they appear in the generator:

### 1. Evidence on every architecture or debugging answer

`Example.is_valid()` rejects records with empty `evidence`. Every template that produces an architecture or debugging record passes a non-empty list. The refusal template uses a single `NEGATIVE_EVIDENCE` placeholder; that one is *also* explicitly checked so we do not leak it into normal training.

### 2. Split by repo, component, and time — not random

A random 90/10 split looks fine and lies to you. The model gets credit for predicting evaluation items it has seen near-duplicates of. Use the metadata to split:

- **By repo.** When you ingest real KDE repos, hold out one entire repo for eval.
- **By component.** Within one repo, hold out one or two components. The eval question about `KFileSearcher` lands in `train` only if no eval question about `KFileSearcher` exists.
- **By time.** When commits are ingested, hold out the last six months. The model should not be able to peek at the future.

[../src/dataset/qa_generator.py](../src/dataset/qa_generator.py) currently emits everything as `split=train` because the v0 eval set is hand-authored. The next iteration will branch on `metadata.component` to seed a real split.

### 3. Include "I don't know from evidence" examples

`template_refusal` exists for one reason: the model must learn that the right answer to *"what signal does KFooBarMaker emit?"* is *"I do not see a class named KFooBarMaker."* Without this, the SLM happily fabricates plausible signals and the hallucination rate spikes. The mini-repo eval item `eval:06:refusal` exercises this directly.

### 4. Include ambiguity examples

A real question might be *"which class handles searches?"*. In the mini repo the answer is ambiguous — `KFileSearcher` and `KFileSearchBackend` both qualify. The v0.1 dataset will add ambiguity templates that explicitly enumerate plausible candidates and ask the model to ask a clarifying question.

### 5. Include stale-code examples

KDE evolves; a question grounded in code that no longer exists must be flagged. The v0.1 dataset will include records whose `metadata.deprecated_at = <date>` so the trainer can teach the model to flag the staleness in its answer.

### 6. Include wrong-assumption examples

*"Why does Dolphin use Baloo for thumbnails?"* — it does not. The answer must correct the false premise. The v0.1 dataset will include false-premise templates that point at the *actual* responsible component (here, KFileItemActions and a thumbnailer plugin).

### 7. Never train hallucinated facts

This is the load-bearing rule. The generator must never invent a relation that does not exist in the graph. The templates iterate `nodes_of_type(...)` and pull data via the named queries. If a class has no signals, it produces no signal record. If a QML component has no `CONNECTS_TO` edge, it produces no backend record. If the graph is wrong, fix the graph; do not paper it over with hand-written records.

## Why we never train hallucinated facts

A small model has tiny capacity. Every false fact you train into it costs a true one. Worse, the model cannot tell facts apart; once it has learned `Foo emits BarSignal`, it will produce that claim with full confidence whether or not `BarSignal` exists. Hallucination is the failure mode that wins many small-model evaluations and ruins many small-model deployments.

The graph-grounded discipline gives you a hard floor: the model trained on this dataset cannot claim a signal that the graph does not contain. That alone makes the model usable in a domain where the cost of a wrong answer is high. Chapter [08_debug_reasoning_eval.md](08_debug_reasoning_eval.md) shows the eval that catches regressions.

## Tracing one record end-to-end

For the eval question *"Which D-Bus methods does org.kde.minisearch expose?"*:

```
graph -> nodes_of_type("DbusInterface")
      -> id for org.kde.minisearch
      -> dbus_methods_of(g, iface) -> [searchPath, cancel, currentPath]
      -> instruction = "Which D-Bus methods does the org.kde.minisearch interface expose?"
      -> output      = "org.kde.minisearch exposes: searchPath, cancel, currentPath.
                        You can call them with `qdbus org.kde.minisearch /<obj> <method>`."
      -> evidence    = [iface, searchPath, cancel, currentPath]
      -> task_type   = "tool_use"
```

That record then gets written to `artifacts/datasets/mini_repo_sft_v0.jsonl`. At inference, the trained model — or the v0 RAG renderer in [../src/rag/answer_with_evidence.py](../src/rag/answer_with_evidence.py) — must produce an answer that mentions `searchPath` and `cancel`. The eval grader compares the answer against `must_mention=["searchPath", "cancel"]`. The pass rate is one of the six numbers in the eval report.

## Where the dataset goes next

Open the TODO and the CHANGELOG for the planned upgrades:

- **More templates.** Function-call / tool-use templates for `ripgrep`, `qdbus`, `journalctl`, `ctest`, `git blame`. Each becomes a template that generates *"to do X, run this command with these arguments and look for Y in the output"* records.
- **Preference data.** For DPO/ORPO, pair every record with one or more `negative_examples`. The negative is a plausible-but-wrong answer; the contrast teaches the model what *not* to say.
- **Real-repo ingestion.** When `configs/repos.yaml` points at a KIO + KConfig + Dolphin slice, the same templates produce orders of magnitude more records. The split rules above start to matter.
- **Adapter routing labels.** Each record's `task_type` becomes the label for the small router classifier in chapter 07.

2. Pick one record and verify its `evidence` by hand: open the named file, find the named symbol, confirm the relation is what the record claims.
3. Add a new template `template_property_signal_pair` that emits *"Which property and signal pair fires on `currentPath` change?"*. What graph queries do you need? What evidence does it carry?
4. Implement a small `validate.py` that loads the JSONL and asserts the seven quality rules. Add a CI test that runs it.
5. Sketch the schema for a `function_calling` task type — what extra fields does it need to carry to teach the model to *issue* a `qdbus` call (and parse the response)?

## Further reading

- *InstructGPT* (Ouyang et al., 2022) for the instruction-tuning frame.
- *Self-Instruct* (Wang et al., 2022) for template-driven dataset generation, and the follow-up *Self-Rewarding Language Models*.
- The *DPO* paper (Rafailov et al., 2023) for the preference-data discipline that v0.1 plans to use.
- "Datasets for Large Language Models: A Comprehensive Survey" — search arXiv for the most recent.
- The HuggingFace `datasets` documentation, particularly the `DatasetDict` patterns for managing splits.
- Andrej Karpathy's *State of GPT* talk for an intuition of how dataset quality dominates over base-model choice in the SFT regime.
- The dolly, alpaca, and oasst dataset cards — they are good antipatterns to compare against (each has known leakage or quality issues).
